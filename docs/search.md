# Поиск и агрегация инцидентов

С чего начинать. Не схема обменника — набор полей, без которых нельзя
ответить на два вопроса: «найди эти события» и «что сейчас происходит».

Инцидент здесь — решение модуля `deny` или `redirect`. `allow` в лог
пишем, в поиск по умолчанию не кладём. `score` инспектора без порога —
не инцидент, а сырьё для калибровки.

## Что ищут

Живой UX ищет по `ray`, `node`, `host`, `uri`, `code`, имени инспектора,
`reason_code`. Это и есть первый индекс.

| Вопрос | Поля |
| --- | --- |
| Этот запрос | `ray` (+ `node`, если он известен) |
| Эта нода / этот сайт / этот путь | `node`, `host`, `uri` |
| Какой маршрут | `server_name`, `location` |
| Чем кончилось | `verdict` |
| Почему модуль отказал | `code` — закрытый набор из восьми значений |
| Кто виноват, если виноват один | `verdict_by`, дальше `inspectors_verdict[имя]` |
| Кто промолчал | `inspectors_state` |
| Какое правило CRS | `reason_rule` / `matched_id` у modsec |
| Какой адрес | `client_ip` |
| Откуда пришли | `country=`, `asn=` — словарь по каталогу пространства, не колонка |
| Когда | `ts` |

Поиск по `ray` окном не сужается: `ray` уникален по флоту, и ограничивать его
сутками значит не находить вчерашний инцидент по ссылке из тикета. Все
остальные фильтры без окна не выполняются.

`code` заменил разом `deny_code`, `by_score`, `by_local` и `fail_reason`: одна
ветка решения — одно значение, и три булевых флага вместе с сырой строкой
правила больше не нужны.

`uri` для фильтра — как пришло, без нормализации. Агрегировать по сырому
пути с query нельзя: каждый `ray` уникален. Для топов позже `uri` без
`args` (якорь уже так и шлёт) хватает.

`reason_text` и `matched_msg` — карточка, не фильтр. Полнотекст по ним
не строим.

## Что считают

Пять запросов закрывают смену. Остальное — уточнение.

```sql
-- 1. динамика отказов
SELECT toStartOfMinute(ts) AS t, verdict, count()
FROM waf.audit
WHERE ts > now() - INTERVAL 1 HOUR AND verdict IN ('deny', 'redirect')
GROUP BY t, verdict;

-- 2. чем отказываем
SELECT code, count()
FROM waf.audit
WHERE ts > now() - INTERVAL 1 HOUR AND verdict = 'deny'
GROUP BY code
ORDER BY count() DESC;

-- 3. куда бьют
SELECT host, count()
FROM waf.audit
WHERE ts > now() - INTERVAL 1 HOUR AND verdict = 'deny'
GROUP BY host
ORDER BY count() DESC
LIMIT 20;

-- 4. какие правила (таблица находок, не позвоночник)
SELECT rule, count()
FROM waf.audit_finding FINAL
WHERE ts > now() - INTERVAL 1 HOUR AND rule != ''
GROUP BY rule
ORDER BY count() DESC
LIMIT 20;

-- 5. порог: плотность у края
SELECT
    quantile(0.50)(score) AS p50,
    quantile(0.99)(score) AS p99,
    countIf(score >= deny_at) AS blocked,
    countIf(abs(score - deny_at) <= 10) AS near_edge
FROM waf.audit
WHERE ts > now() - INTERVAL 1 HOUR AND deny_at > 0;

-- 6. кто атакует
SELECT client_ip,
       dictGetOrDefault('waf.geo_country', 'code', client_ip, '') AS country,
       count()
FROM waf.audit
WHERE ts > now() - INTERVAL 1 HOUR AND verdict IN ('deny', 'redirect')
GROUP BY client_ip, country
ORDER BY count() DESC
LIMIT 20;

-- 7. кто тормозит контур
SELECT name, quantile(0.99)(latency) AS p99
FROM waf.audit
ARRAY JOIN
    mapKeys(inspectors_latency_ms) AS name,
    mapValues(inspectors_latency_ms) AS latency
WHERE ts > now() - INTERVAL 1 HOUR
GROUP BY name
ORDER BY p99 DESC;
```

`crs_would_block` на спутнике — калибровка, не инцидент: CRS уже перешёл
свой порог, модуль мог пропустить. Считать отдельно от `verdict = deny`.

## Минимум колонок

Согласованный позвоночник — одна строка на запрос:

`node` + `ray` + `client_ip` + `status` + `verdict` + `code` + `verdict_by` +
`score` + `host` + `uri` + `method` + карта участников.

`id` в разговоре — это `node` (`waf_node_id`). Отдельный uuid для строки не
нужен: `ray` и есть uuid запроса, `node` при нём — чтобы не искать по флоту.

```json
{
  "ts": "2026-08-15T10:00:00.123Z",
  "node": "edge-01",
  "ray": "11d4ea9c-80b2-4c7e-9f01-6a5b4c3d2e10",
  "client_ip": "203.0.113.10",
  "method": "GET",
  "host": "app.example.com",
  "uri": "/",
  "status": 403,
  "verdict": "deny",
  "code": "score",
  "by": "module",
  "score": 50,
  "inspectors": ["ip", "modsec"],
  "vars": { "country": "ru", "asn": "15169" }
}
```

| Поле | Смысл |
| --- | --- |
| `node`, `ray` | ключ. `phase` пока всегда `request` |
| `client_ip` | топ «кто» без IP не собирается |
| `vars` | стандартный набор модуля (User-Agent, Referer, XFF, Accept-Language, Origin, Content-Type, Accept, `request_id`) всегда; остальное — страна, ASN — через `waf_var` |
| `method`, `host`, `uri` | куда. `uri` без query — так якорь и шлёт |
| `status` | код клиенту после apply. На `allow` фазы запроса `0`: апстрим ещё не ответил |
| `verdict` | решение **модуля**: `allow` / `deny` / `redirect`. Не `score` |
| `code` | почему; закрытый набор, пусто ровно на `allow` |
| `verdict_by` | чей вердикт стал итогом: `module` либо имя инспектора |
| `score` | 0, если никто не ставил. Порог перешли — всё равно `verdict=deny` |
| `inspectors` | кого **звали**. Рядом карты на инспектора: `inspectors_verdict`, `inspectors_state`, `inspectors_score`, `inspectors_latency_ms`, `inspectors_role`, `inspectors_profile`. Строку «score [50]» не храним — она собирается на SELECT. `has(inspectors, 'modsec')` для фильтра не трогаем |

`score` инспектора (`modsec` ответил `verdict: score`) на позвоночник
не ставим третьим исходом: модуль уже сложил вклады и либо отказал,
либо пропустил. Иначе список врёт — «score» при 403.

`redirect` не выкидывать: челлендж так и выглядит.

`inspectors` — кого спросили, не «кто что-то нашёл». Чисто тоже
событие. Кто ответил `score`/`deny` — на карточке и в находках.
Кто не ответил — в `inspectors_state`: `timeout`, `absent`, `skipped`.

`client_ip` теперь на якоре, страна и ASN считаются на запросе словарём по
каталогу пространства ([tables.md](tables.md#страна-и-asn-словарями)). Своего
geo у модуля нет и не будет, колонок в записи под них тоже: адрес известен, а
кому он принадлежал — знает каталог, и он же отвечает задним числом на то, что
записано до его заливки.

**Находки** — по строке на каждую, от любого инспектора:

| Поле | Зачем |
| --- | --- |
| тот же ключ | карточка одного `ray` |
| `rule`, `code` | агрегат 4 и поиск «где стреляло 913100»; оба под bloom-фильтром |
| `severity`, `target` | что и где нашли |
| `inspector`, `profile`, `verdict`, `score` | чей движок и с какой настройкой; повторены на строке ради поиска без JOIN |
| `engine` | своё движка: `crs_anomaly_score`, `gen`, метки модели |

Отдельной таблицы на инспектора нет: форма находки одна на всех, и «сколько
913100» читается одной таблицей, а не `UNION` по спутникам.

Якорь и находки — своя доставка у каждого, и друг друга они не ждут. Поэтому
карточка сводит обе стороны на чтении, а «звали, а строк находок нет» видно по
их отсутствию, а не по колонке на позвоночнике.

## Чего не нужно, чтобы начать

| Кажется нужным | Почему нет |
| --- | --- |
| Текст правила, `matched_data` | карточка, не индекс |
| Все инспекторы в JSON на позвоночнике | раздувает скан списка |
| Тело / архив | разбор одного `ray`, не топ |
| Ответ апстрима | фазы нет; инцидент на запросе уже есть |
| Полнотекст по URI | префикс `uri` и `host` закрывают топ |
| `engine_ms` инспектора | операции, не инциденты; round-trip уже есть в `inspectors_latency_ms` |

## Как у других

Один и тот же куб. Cloudflare Security Events, AWS WAF logs, Akamai SIEM,
F5/NAP, Imperva CEF — список и топы строят из одних измерений. Карточка
богаче, индекс нет.

| Измерение | Cloudflare | AWS WAF | Akamai | F5 / NAP | Imperva | У нас |
| --- | --- | --- | --- | --- | --- | --- |
| id события | RayID | requestId | requestId | support_id | — | `ray` |
| действие | Action | action | appliedAction | request_status | REQ_BLOCKED | `verdict` |
| кто | ClientIP, Country, ASN | clientIp, country | clientIP, geo.asn/country | ip_client | src, geo | `client_ip`, страна и ASN словарём |
| куда | Host, Path, Method, UA | uri, method, headers | host, path, query | host, uri, method | url, site | `host`, `uri`, `method` |
| чем отсекли | Source + RuleID | terminatingRuleId | rules[] + policyId | violations + signature | Attack ID / rule name | `code` + `verdict_by` |
| класс атаки | Source (waf/ip/bot) | rule type | ruleTags (OWASP) | attack_type, VIOL_* | Attack Severity / name | нет тега CRS, только id |
| счёт | bot/WAF/AI scores | — | vector score в ruleData | violation_rating 0–5 | severity | `score` / `deny_at` / CRS |
| где совпало | Metadata | location (SQLi/XSS) | ruleSelectors | parameter / context | parameter_name | нет |
| политика | Zone | webaclId | configId, policyId | policy_name | site / account | `server_name` + `location`, профиль в `inspectors_profile` |

Топы в их UI одни и те же: действие по времени, IP, страна, ASN, host,
path, UA, правило, тип атаки. Тело и сырой match — не в индексе.
AWS `ruleMatchDetails` заполняет только SQLi/XSS. F5 сырой request
кладёт в карточку по support_id. Cloudflare список ещё и сэмплирует.

Чего у лидеров нет в поиске, и нам тоже не надо на первом шаге:
полный body, все заголовки, текст каждого правила.

Чего у них есть, а у нас дыра для тех же топов:

1. **Класс атаки, не только id правила.** Akamai/F5/Imperva агрегируют
   `XSS` / `SQLi` / `command injection`. У CRS это тег
   (`attack-sqli`, `OWASP_CRS/WEB_ATTACK/...`). `913100` в топе
   оператору менее понятен, чем «сканер».
2. **Где совпало** — параметр или заголовок. У нас этого нет ни на
   позвоночнике, ни у спутника.

Источник решения как низкая кардинальность у нас закрыт: `code` — ровно то
измерение, которое Cloudflare зовёт Source, а F5 — attack_type источника.

`User-Agent` у Cloudflare в топах Security Events. У нас он живёт в
`vars['user_agent']` — стандартный набор модуля, без объявления.

## Ручки

`waf-search` (`:8091`). UX ходит в `/api/search/...` на контроллере, тот
проксирует сюда один в один.

| Ручка | Что отдаёт |
| --- | --- |
| `GET /api/audit` | список; фильтры выше, `limit`/`offset`, `total`, `?order=asc` — с начала окна вместо конца. Превью в списке не отдаётся |
| `GET /api/audit/groups` | группы того же фильтра по осям `?by=ip,uri` (до четырёх из `ip`, `host`, `uri`, `method`, `status`, `verdict`, `code`, `by`, `node`, `phase`, `marker`, `user`); на группу — значения осей, `hits`, `denied`, `last`. `?sort=` — метрика (`hits`, `denied`, `last`) или выбранная ось, `?dir=asc\|desc`; умолчание — крупные сверху. Пустой `by` — 400 |
| `GET /api/audit/{node}/{ray}` | одна запись, той же формы, что элемент списка, плюс превью запроса |
| `GET /api/audit/{node}/{ray}/inspectors` | разбор по участникам с находками |
| `GET /api/audit/{node}/{ray}/findings` | те же находки плоским списком, для выгрузки |
| `GET /api/audit/{node}/{ray}/headers` | сырые заголовки из обменника, парами; `offset`/`limit` — окно |
| `GET /api/audit/{node}/{ray}/args` | строка запроса как пришла и её параметры |
| `GET /api/audit/{node}/{ray}/body` | тело: текстом либо base64 |
| `GET /api/findings` | поиск по правилу поперёк запросов |

Ключ записи — `node` и `ray`, `phase` необязательным параметром: по умолчанию
берётся `request`. `ray` уникален по флоту, `node` при нём — чтобы не искать
по всему обменнику.

Разворот записи разложен по ручкам не ради красоты URL, а потому что стоят они
разного. Список сканирует сутки; разбор по инспекторам — вторая таблица;
содержимое — поход в Redis или S3 за объектом, которого в ClickHouse нет вовсе.
Одна ручка на всё платила бы за всё сразу и на каждой строке.

Карточка открывает сначала инспекторов и ходит за содержимым только тогда,
когда открыли соответствующую вкладку.

### Поиск по превью

Три фильтра поверх колонок превью — единственный способ искать по содержимому
запроса, не открывая каждую запись по очереди:

| Параметр | Пример | Условие |
| --- | --- | --- |
| `header=<имя>[=<значение>]` | `header=user-agent=curl/8.5` | `headers_preview['user-agent'] = ...` |
| `param=<имя>[=<значение>]` | `param=redirect` | `args_preview['redirect']`, любое значение |
| `body=<подстрока>` | `body=union select` | `lower(body_preview) LIKE '%…%'` |

Имя без значения спрашивает о наличии ключа, а не о равенстве пустой строке:
«у кого вообще был `X-Api-Key`» спрашивают не реже, чем «у кого он равен».
Несколько пар складываются по И, как `var=`. Имя заголовка приводится к нижнему
регистру — таким его записал логгер; имя параметра нет, регистр в нём значим.

Ищут по `lower(body_preview) LIKE`, а не `positionCaseInsensitive`: выражение
обязано совпасть с выражением skip-индекса `idx_body_preview`, иначе ngram-фильтр
не включится и запрос прочитает все куски партиции. `%` и `_` в игле
экранируются — это символы запроса, а не шаблон.

Найти можно только то, что попало в превью: секретные заголовки в нём
отсутствуют по построению, а срез ограничен бюджетами модуля. Пустой ответ на
`body=` не означает, что в теле этого не было, — только что этого не было в
первых килобайтах.

То же и с потолком на пару: `header=x-trace=abcd1234` не найдёт запрос, у
которого значение урезано до `abcd`. Точное сравнение по урезанному значению
вообще не отвечает, поэтому карточка называет такие имена —
`headers_preview_truncated` и `args_preview_truncated`, — а пары, выброшенные
целиком, считает в `*_preview_dropped`.

Превью отдаётся карточкой, но не списком: 200 событий по 40 КБ среза — это
мегабайты на страницу, из которых видно две строки.

### Поиск по сессиям

| Параметр | Пример | Условие |
| --- | --- | --- |
| `user=<логин>` | `user=alice` | `has(sessions_user, ...)` |
| `user=<источник>:<логин>` | `user=corp:alice` | `arrayExists(...)` по паре |
| `session=<идентификатор>` | `session=sha256:ab12…` | `has(sessions_id, ...)` |

Логин и идентификатор — из секции `sessions` записи: чьи сессии назвали
инспекторы (своя калитка, чужой JWT, кука приложения), см.
[tables.md](tables.md#сессии-sessions_). Совпадение точное, с любой записью
массива; оба параметра складываются по И, как `var=`. Идентификатор — не
кука: `sid`, claim токена либо хеш, и искать по значению куки бессмысленно.

Личность — пара «источник входа : логин», и `user=` принимает обе формы.
Голый логин отвечает на «этот логин у кого угодно», пара — на «этот человек»:
`alice` своей калитки и `alice` из чужого JWT совпадают именем и больше ничем,
пространство имён задаёт источник. Двоеточие делит по первому вхождению —
имени источника его не дают, а логин бывает урной (`corp:urn:user:1` — это
источник `corp`). Логин, в котором двоеточие есть, ищут с пустым источником:
`:urn:user:1` — тот же `has()` по логину целиком.

Той же парой группируют: `by=user` разворачивает массивы в строки
`источник:логин` (`arrayJoin`), пропуская сессии без имени; запись без сессий
в группировку не попадает вовсе. Ключ группы — законное значение `user=`, и
разворот группы обратно в список даёт ровно её строки.

### Поиск по маркерам

| Параметр | Пример | Условие |
| --- | --- | --- |
| `marker=<метка>` | `marker=bot-farm` | `has(markers, ...)` |

Метка — из секции `markers` записи: что попросили пометить инспекторы глаголом
`mark` (`inspector-actions.md`). Совпадение
точное и строкой целиком: метку пишет оператор, и подстрока по массиву тут
означала бы «похоже на то, что он имел в виду».

Той же меткой группируют: `by=marker` разворачивает массив (`arrayJoin`), и
запись без меток в группировку не попадает вовсе.

### Содержимое: только архив

В записи лежит локатор, содержимое — в архиве. Горячего обменника поиск не знает
и знать не может: Redis — внутренний контур волны, и до читателя записи объект
там не доживает никогда. Всё, чего маршрут не назвал в `waf_archive request`,
модуль удаляет сразу после вердикта. Всё, что назвал, забирает агент — и
публикует запись, уже подменив адресацию архивной, а обменник чистит последним
шагом, после публикации. Промежуточного состояния «в записи горячий адрес, а
ключ ещё жив» поэтому не существует: адресация в записи либо архивная
(`"store": "archive"`, `"driver": "s3"`), либо её нет вовсе.

Отсюда и потолок покрытия: карточка покажет ровно то, что перечислено в
`waf_archive request` на маршруте. Не архивируется — не будет видно, и никакая
настройка поиска этого не изменит. Названный там размер (`body=8k`) — второй потолок:
объект уехал в архив префиксом, и локатор говорит об этом `truncated`.

«Содержимого нет» — обычный ответ `200` с `available: false` и причиной, а не
отказ. Запись существует, размер и контрольная сумма верны и часто отвечают на
вопрос без байтов; `404` на это прятал бы от разбирающего инцидент всё
остальное. Причины называют трое: модуль (`oversize`, `store_unconfigured`,
`streaming_not_supported`, `transform_failed`), агент (`expired`, `empty`,
`overload`, `archive_error`) и сам поиск (`absent`, `discarded`, `ttl_expired`,
`store_disabled`, `driver_unsupported`, `store_error`).

`discarded` — самая частая: локатор есть, размер верен, адресации нет. Так
выглядит объект, не переживший вердикт, и объект, который инспектор просил
уровнем `meta` — такой в обменник не попадал вовсе.

`ttl_expired` — адрес есть, но `expires_at` локатора уже прошёл: объект удалило
lifecycle-правило бакета. Ответ даётся без похода в архив — тот вернул бы то же
самое, но на round-trip позже. Срок в записи — обещание правила, а вычищает
объекты сканер хранилища, поэтому ответ бывает раньше самого удаления; это
осознанный выбор в пользу того, чтобы карточка дважды отвечала одинаково.
Отличается от `expired`, который значит «в архив сходили, объекта там нет»: у
первого правило известно, у второго — нет.

Ни на что не жалуется и в архив не ходит тот, у кого срока в локаторе нет вовсе:
правила удаления в бакете не заведено, объект переживёт запись, и поиск идёт за
ним как обычно.

Заголовки и параметры едут парами, а не объектом: порядок значим, а дубликаты
имён (`Set-Cookie`, `Forwarded`, подменённый параметр) в объекте потерялись бы —
и ровно они бывают тем, из-за чего запрос отсекли.

Карточка не забирает объект целиком: `?offset=&limit=` — окно в байтах, следующее
подгружается по scroll. Без этих параметров ответ прежний, одним куском до
`WAF_STORE_MAX_BYTES`. `clipped` значит, что за окном в объекте ещё есть байты,
а не то, что модуль не дочитал тело — это `truncated` локатора. Потолок —
потолок одного окна, не всего объекта: дальше карточка просит следующее.

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `WAF_STORE_S3_ENDPOINT` | — | Архив |
| `WAF_STORE_S3_REGION` | `us-east-1` | Регион для подписи SigV4 |
| `WAF_STORE_S3_CREDENTIALS_FILE` | — | Реквизиты файлом, как у агента |
| `WAF_STORE_S3_ACCESS_KEY`, `WAF_STORE_S3_SECRET_KEY` | — | Они же переменными |
| `WAF_STORE_BUCKET_HEADERS`, `_ARGS`, `_BODY` | — | Бакет по виду. Пусто — архив этого вида поиску не открыт |
| `WAF_STORE_MAX_BYTES` | `262144` | Потолок одного окна чтения |
| `WAF_STORE_OP_TIMEOUT` | `5s` | Таймаут одного похода в обменник |

Ничего не задано — чтение архива выключено, и это не ошибка: поиск по
позвоночнику работает и без него, а карточка честно скажет `store_disabled`.
Бакеты — те же, что у агента (`WAF_RETAIN_BUCKET_*`).

## Индекс

Позвоночник: `ORDER BY (ts, node, ray, phase, frame_direction, frame_seq)`.
Ключ склейки `(node, ray, phase, frame_direction, frame_seq)` — единственное,
по чему запись обязана быть одна, и он в ключе целиком; дедуп за
ReplacingMergeTree, at-least-once на шине иначе даёт две строки на событие.
Но ведёт ключ временем ([024](../schema/024_audit_v4.sql)): каждый
вопрос журнала — окно времени, и с `ts` в голове окно отсекает первичный
индекс, «последние 50» читаются с хвоста ключа и останавливаются на `LIMIT`,
а куски ложатся встык, так что `FINAL` сводит только их границы. С прежним
ключом при случайном `ray` список за сутки читал и сортировал полтора
миллиона строк на каждую страницу, а `FINAL` сливал все куски партиции
заново: на стенде это секунда-полторы на любой вопрос.

Что читается как:

| Запрос | `FINAL` | Почему |
| --- | --- | --- |
| список, находки списком | нет | под `FINAL` в 24.8 чтение по порядку ключа выключено; дубль снимает страница по ключу склейки |
| счёт, группы | да | читают окно целиком, и дубль до слияния сосчитал бы себя дважды. Число групп едет в той же строке, что группы (`count() OVER ()`): второй проход по окну ради счёта стоил столько же, сколько первый |
| карточка по `ray`, находки карточки | да | строк единицы, bloom по `ray` ведёт и под `FINAL` |

Skip-индексы под `FINAL` в 24.8 по умолчанию выключены
(`use_skip_indexes_if_final`): ClickHouse боится пропустить гранулу с более
свежей версией строки. Версий у нас нет — `rev` всегда 0, дубль одинаков байт
в байт, — и поиск включает настройку на соединении (`internal/ch/ch.go`). До
этого ни один skip-индекс таблиц не работал вовсе.

Индексы позвоночника и что их включает:

| Индекс | Вопрос | Условие в запросе |
| --- | --- | --- |
| `idx_ray` bloom | карточка по ссылке, без окна | `ray = @ray` |
| `idx_client_ip` bloom | «что делал этот адрес» | `client_ip IN (toIPv6(...))` — одиночный адрес; сеть идёт диапазоном `>= … AND <= …` и индекс не трогает |
| `idx_uri` ngram по `lower(uri)` | подстрока в пути | `lower(uri) LIKE '%…%'`, не `positionCaseInsensitive` |
| `idx_body_preview` ngram по `lower(body_preview)` | подстрока в теле | то же |
| `idx_sessions_user`, `idx_sessions_id` bloom | «что делала alice», «что делала эта сессия» | `has(sessions_user, …)`, `has(sessions_id, …)` |
| `idx_markers` bloom | «всё, помеченное bot-farm» | `has(markers, …)` |

Фильтры по вердикту, коду, методу, статусу индекса не имеют намеренно: `deny`
есть почти в каждой грануле окна, и bloom по нему ничего бы не отсёк. Их
цена — чтение узкой `LowCardinality`-колонки по окну, и это дёшево.

Находки: `ORDER BY (ts, node, ray, phase, inspector, finding_idx,
frame_direction, frame_seq)` по тем же причинам ([028](../schema/028_audit_finding_v2.sql)),
bloom по `rule`, `code` и `ray`.

Стенд, 1.9 млн строк за сутки и 14 млн находок на двух ядрах, до и после:

| Запрос | было | стало |
| --- | --- | --- |
| список за сутки, страница | 1.3 с | 30 мс |
| счёт за сутки | 0.5 с | 13 мс |
| карточка по `ray` | 0.9 с | 35 мс |
| группы по адресу (1.3 млн разных) | 0.8 с | 0.3 с |
| группы по стране | 0.9 с | 0.28 с |
| один адрес, счёт | 0.2 с | 14 мс |
| находки по правилу | 1 с | 7 мс |

Группы упираются уже в саму агрегацию окна, а не в чтение.

Спутник modsec: `ORDER BY (toStartOfHour(ts), reason_rule, ray)`.
Топ правил не должен сканировать позвоночник.
